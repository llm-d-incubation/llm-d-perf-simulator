BLIS blackbox inference simulator an incubating component of llm-d

Know how a serving configuration performs before you book the accelerators.

BLIS is a discrete-event simulator for LLM serving. It models admission, routing, scheduling, batching and KV-cache behaviour on a CPU, pricing each forward pass from a model graph, a chip and calibrated coefficients, then sweeps that over configurations: tensor parallelism, instance counts, batch limits.

Metrics it predicts tok/s per accelerator per-user tok/s TTFT p99 TPOT E2E p95

TTFT is time to first token, TPOT the time per output token, E2E the end-to-end request latency.

How the numbers stay honest

Every figure traces back to a versioned input.

Each input a prediction depends on lives in its own versioned repository, so any number here can be traced to the exact version that produced it. The accuracy dashboard reports how far those predictions sat from measured runs, per model.

blis-catalog inputs Models, hardware and workloads, pinned. blis-registry calibration Coefficients, fitted globally and versioned. blis-latency-kernel pricing Every step time and memory figure. blis-vllm engine vLLM behaviour, pinned to one release. blis-schemas contracts What passes between the four others.

Where this fits

BLIS is an incubating component of llm-d, the Kubernetes-native stack for distributed LLM inference. llm-d deploys and scales serving engines across a cluster; BLIS answers the question that comes first, which is what to deploy. The engine flags a search returns, things like max-num-seqs, max-num-batched-tokens and tensor-parallel width, are the knobs you then set on a real deployment.

The simulator runs llm-d's own router. Every multi-instance cluster routes through the real Endpoint Picker embedded in-process, reading a deployment's own EndpointPickerConfig, EPP flags and InferencePool and InferenceObjective manifests, so the routing config you simulate is the one you deploy. Admission and flow control come from the router too.

That loop has already returned policies to llm-d. Two were found in simulation, validated on hardware and merged: a probabilistic admitter and a soft-reflective flow-control ceiling, both cutting tail latency substantially on overloaded workloads. Each has a write-up giving the numbers and the method.
