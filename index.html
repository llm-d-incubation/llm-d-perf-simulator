BLIS llm-d performance simulator an incubating component of llm-d

Know how a serving configuration performs before you book the accelerators.

BLIS is a digital twin of llm-d: a discrete-event simulator that models admission, routing, scheduling, batching and KV-cache behaviour on a CPU, pricing a serving configuration from a model graph, a chip and calibrated coefficients, without touching an accelerator. Evaluating a configuration is cheap, so thousands can be swept to find the best.

Use case

Config search

Sweep serving configurations, tensor parallelism, instance counts and batch limits, pricing each one with BLIS, and keep only the Pareto-optimal few: the configurations no other beats on both throughput per accelerator and per-user speed. The reports are published in the config-search dashboard.

simulate → validate → merge

Use case

Policy discovery

Discover serving policies in simulation, admission, routing and flow control, then validate the promising ones on hardware and merge them upstream. The simulator runs llm-d's own router, so a policy that works in simulation is the one you deploy.

In production: three policies discovered with BLIS and merged into llm-d.

  • probabilistic admitter sheds low-priority requests under load so critical ones stay fast
  • soft-reflective ceiling throttles smoothly near capacity to hold down tail latency
  • lora-residency scorer routes LoRA requests to pods already holding the adapter

How it fits

BLIS is a digital twin of llm-d, the Kubernetes-native stack for distributed LLM inference. It is an incubating llm-d component: llm-d deploys and scales serving engines across a cluster, and BLIS answers the question that comes first, which is what to deploy. The flags a search returns, max-num-seqs, max-num-batched-tokens and tensor-parallel width, are the knobs you then set on a real deployment.

It is a twin because it runs llm-d's own code, not a model of it. Every multi-instance cluster routes through the real Endpoint Picker embedded in-process, reading a deployment's own EndpointPickerConfig, EPP flags and InferencePool and InferenceObjective manifests, so the routing config you simulate is the one you deploy. Admission and flow control come from the router too.
