Know how a serving configuration performs before you book the accelerators.

BLIS prices one forward pass from a model graph, a chip and calibrated coefficients, then sweeps that over configurations: tensor parallelism, instance counts, batch limits. It predicts fleet throughput, per-user token rate and tail latency for a given model, accelerator budget and workload.

How the numbers stay honest

Every figure traces back to a versioned input.

A prediction is only worth as much as what went into it. The pieces below are separate, versioned repositories rather than one bundle, so a number on this site can be traced to the catalog entry it came from, the coefficient set in force at the time, and the kernel that priced it. The accuracy dashboard then reports how far those predictions sat from measured runs, per model.

blis-catalog

Models, hardware and workload types. Pinned and read-authoritative, so a scenario means the same thing on every run.

view repository

blis-registry

Calibration coefficients, versioned. Fitted globally and reused, which is what removes the per-model profiling run.

view repository

blis-latency-kernel

Prices one forward pass from a model graph, a chip and the coefficients. Every step time and memory figure comes from here.

view repository

blis-schemas

The contracts between the three above: models, hardware, coefficients, deployments and the kernel interface.

Where this fits

BLIS is an incubating component of llm-d, the Kubernetes-native stack for distributed LLM inference. llm-d deploys and scales serving engines across a cluster; BLIS answers the question that comes first, which is what to deploy. The engine flags a search returns, things like max-num-seqs, max-num-batched-tokens and tensor-parallel width, are the knobs you then set on a real deployment.

Two policies found in simulation have since been validated on hardware and merged into llm-d: a probabilistic admitter and a soft-reflective flow-control ceiling, both cutting tail latency substantially on overloaded workloads. The write-ups below give the numbers and the method. Running llm-d's own router code inside the simulator, so one routing config can be simulated and then deployed unchanged, is a design under discussion rather than something you can do today.
